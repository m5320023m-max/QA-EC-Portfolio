# 1. テスト分析
主要フローが成立するために必要な処理について整理した。
- 会員登録
- 会員情報の引き継ぎ
- 購入処理
- 注文・決済処理
- 状態
- ユーザーへの結果表示  
また、一連のフローを阻害する入力不備、重複操作、処理中断、決済異常についても確認対象とする。

| ID | 分析対象 | 確認する内容 |
|---|---|---|
| A1 | 主要フローの完結性 | 新規会員登録から注文完了まで、一連の主要フローを正常に完了できること |
| A2 | 会員登録 | 有効な会員情報を入力した場合、新規会員として正常に登録されること |
| A3 | 会員登録時の入力 | 必須項目や入力形式に問題がある場合、不正な状態で会員登録が成立しないこと |
| A4 | 会員状態 | 会員登録の成功・失敗に応じて、正しい会員状態になること |
| A5 | 登録後の購入導線 | 会員登録完了後、登録した会員として購入フローを継続できること |
| A6 | 会員情報の引き継ぎ | 登録したユーザー情報が購入処理へ正しく引き継がれること |
| A7 | 注文データ | 商品、数量、金額、配送先、支払方法が注文処理へ正しく引き継がれること |
| A8 | 注文処理 | 注文確定、決済、注文番号発行、注文状態の確定まで正常に完了すること |
| A9 | 注文・決済状態 | 正常時・異常時ともに、注文状態と決済状態に不整合が残らないこと |
| A10 | 結果通知 | 会員登録完了および注文完了をユーザーが認識できること |
| A11 | 重複操作 | 連打、ページ更新、再操作によって同一注文・決済が重複して成立しないこと |
| A12 | 処理中断 | 通信断やブラウザ終了が発生しても、不整合な注文・決済状態が残らないこと |
| A13 | 決済異常 | 決済失敗や決済結果不明の場合、注文状態を誤って確定しないこと |
| A14 | 外部決済結果 | 決済サービスの結果が確認できた場合、その結果が注文状態へ正しく反映されること |

# 2. テスト観点一覧
「テスト観点」は主要フローにおいて確認したい性質、
「条件・バリエーション」はその性質を確認するための具体的な状況として整理する。

## 2-1. 新規会員登録
| 大分類 | テスト観点 | 条件・バリエーション | 確認内容 |
|---|---|---|---|
| 処理 | 会員登録の完結性 | 正常登録 | 必要な処理が最後まで完了し、新規会員として登録される |
| データ | 登録情報の正確性 | 正常登録 | 入力した会員情報が意図せず変化せず登録される |
| 入力 | 必須項目・入力制約 | 未入力・形式不正 | 不正な入力内容では会員登録が成立しない |
| データ | 重複会員の防止 | 登録済み情報を使用 | 仕様上許可されない重複会員が作成されない |
| 状態 | 会員状態の整合性 | 登録成功・登録失敗 | 処理結果に応じた正しい会員状態になる |
| UI | 登録結果の認識 | 正常登録 | ユーザーが会員登録完了を認識できる |

## 2-2. 会員登録から購入への接続
| 大分類 | テスト観点 | 条件・バリエーション | 確認内容 |
|---|---|---|---|
| 画面遷移 | 登録後の購入導線 | 会員登録成功 | 登録完了後、購入フローへ正常に進める |
| 連携 | 会員情報の引き継ぎ | 登録→購入 | 登録したユーザーとして購入処理を継続できる |
| 状態 | 認証・会員状態の継続 | 登録後の購入操作 | 購入途中で会員状態が失われず、対象ユーザーとして処理される |

## 2-3. 購入・注文確定
| 大分類 | テスト観点 | 条件・バリエーション | 確認内容 |
|---|---|---|---|
| 処理 | 主要フローの完結性 | 新規登録→正常注文 | 会員登録から注文完了までの一連の処理が正常に完了する |
| データ | 注文内容の正確性 | 商品・数量・配送先・支払方法 | 選択・入力した内容が注文へ正しく反映される |
| データ | 金額の正確性 | 正常注文 | 注文時の金額が意図した内容と一致する |
| データ | 注文番号の正当性 | 注文成立 | 注文成立時に注文番号が正しく発行される |
| 状態 | 注文・決済状態の整合性 | 正常決済 | 決済成功と注文成立が一致する |
| 状態 | 注文・決済状態の整合性 | 決済失敗 | 決済失敗にもかかわらず注文が成立しない |
| 状態 | 注文・決済状態の整合性 | TIMEOUT / UNKNOWN | 結果判明前に注文状態を誤って確定しない |
| 処理 | 重複処理防止 | 注文確定ボタン連打 | 注文・決済が重複して成立しない |
| 処理 | 重複処理防止 | ページ更新 | 注文処理が不正に再実行されない |
| 処理 | 重複処理防止 | 結果未確認後の再操作 | 成立済み注文が重複して成立しない |
| 障害耐性 | 処理中断後の整合性 | 通信断 | 最終的に妥当な注文・決済状態へ確定する |
| 障害耐性 | 処理中断後の整合性 | ブラウザ終了 | サーバー側の注文・決済状態に不整合が残らない |
| UI | 注文結果の認識 | 正常成立 | ユーザーが注文完了を認識できる |

# 3. 主要フローとしての確認
個々の機能だけでなく、以下の一連の流れが成立することを確認する。

**未登録ユーザー**  
↓  
**新規会員登録**  
↓  
**会員登録成立**  
↓  
**登録した会員として購入開始**  
↓  
**商品・配送先・支払方法を設定**  
↓  
**注文確定**  
↓  
**決済成功**  
↓  
**注文成立**  
↓  
**注文番号発行**  
↓  
**注文完了をユーザーが認識**  

この主要フローでは、各処理が単独で成功するだけでなく、
- 会員登録したユーザーとして購入できる
- 登録情報と購入処理が正しく紐づく
- 購入時に入力・選択した内容が注文へ反映される
- 決済結果と注文状態が一致する
- 最終的にユーザーが注文完了を確認できる
ことを確認する。

# 4. モック決済条件
購入フローにおける決済処理の正常・異常状態を確認するため、
モック決済では以下の結果を再現可能とする。

| 結果 | 内容 | 主な確認対象 |
|---|---|---|
| `SUCCESS` | 決済成功 | 注文成立、注文番号発行、注文完了 |
| `FAILED` | 決済失敗 | 注文未成立、注文・決済状態の整合性、再注文可否 |
| `TIMEOUT / UNKNOWN` | 決済結果を取得できない | 結果不明時の状態制御、結果確認後の注文状態反映 |

テスト分析により、主要フローを確認するために以下の仕様を明確にする必要がある。

| 6 | 登録した会員情報のうち、購入処理へ引き継がれる情報 |

| No. | 確認事項 |
|---:|---|

| 8 | 決済処理と注文番号発行の処理順 |
| 9 | 決済結果不明時の状態確認方法 |
| 10 | 決済結果確認の回数・間隔 |
